1. The product is mode-first instead of conversation-first
Jarvis currently separates:

Chat
Voice
Agent
Camera
Browser
Research
Studios
Build tools
The code explicitly tracks separate modes:

'voice' | 'chat' | 'agent' | 'camera'

Web search and agent behavior are also controlled by separate flags. This makes the user decide how Jarvis should work before asking the question.

ChatGPT generally lets the assistant determine whether search, files, analysis, or tools are needed.

This is probably the biggest source of the “unfinished” feeling.

2. The model experience can feel inconsistent
Jarvis uses a key rotation system and can prioritize:

OpenRouter free auto-router

That is useful for availability, but it can produce different model quality, response style, reasoning ability, and tool behavior from request to request.

So even when the UI looks polished, the assistant may feel unpredictable:

One answer is excellent.
The next answer is shallow.
Tool calling may work differently between requests.
Vision or file behavior may vary by provider.
A ChatGPT replacement needs a clearly controlled default intelligence level, not only failover.

3. File handling is much narrower than it appears
Jarvis currently sends one file inline as base64. The backend deliberately handles:

Images
PDFs
Word documents
Plain text
Markdown
JSON
JavaScript/TypeScript
XML/YAML
Other types return:

[Unsupported file type]

That means common ChatGPT workflows are incomplete:

Spreadsheet analysis
CSV analysis
Presentation review
Multiple-file comparison
Reusable project files
Persistent document context
Data analysis with charts and calculations
The attachment UI looks like a general-purpose file feature, but the underlying capability is closer to “single-document extraction.”

4. Conversations are not organized around projects or user context
The current conversation schema contains:

Conversation ID
Title
Type
System prompt
Timestamps
It does not contain a user or project boundary.

That means Jarvis has history and memory, but not a strong project model such as:

“My business”
“This app”
“My job search”
“This research topic”
“This folder of documents”
ChatGPT feels more useful because ongoing context has a home. Jarvis currently makes the user return to isolated conversations or research gems.

5. Deep Research is overpromising relative to the interface
Jarvis advertises research runs lasting:

5–12 hours
1–3 days
1 week+
Potentially weeks
That is a bold feature, but the current flow mainly provides:

A prompt
A depth setting
A mode setting
A progress bar
A few log lines
A report preview
An eventual gem conversation
The UI does not yet give the user the trust controls ChatGPT has:

A proposed plan before starting
Source restrictions
Website selection
Editable research scope
Meaningful source activity
In-progress refinement
A cited, navigable report
A strong connection between the original question and final result
Long-running work needs more transparency than normal chat. Otherwise it feels like launching a black box and hoping something good appears later.

6. There are many panels, but not enough “finished outcomes”
Jarvis has:

Image generation
Camera
Browser automation
Terminal/build mode
Design Studio
Music Studio
Data Lab
Gems
Deep Research
Screen sharing
Voice emotion detection
That is impressive, but each additional panel raises the quality expectation for the entire product. If the user cannot reliably move from intention to finished result, the number of features makes the app feel less focused rather than more capable.
